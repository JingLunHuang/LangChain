# 開發者筆記

## 從課程出發

課程工具鏈示範讓我理解：工具要有清楚的輸入、輸出與描述，Agent 才能選擇適合的操作。網路診斷案例展示多個工具如何串聯；記憶案例讓我理解每輪對話會帶上舊訊息。簡報的 LCEL 部分則提供可組合模組的觀點。來源對應見 [資產盤點](asset-audit.md)。

`筆記20260727.txt` 提出 MCP 工具描述會占上下文、context 滿瞭如何 summary、memory 如何影響緩存等問題。這些問題讓我把作品集的重點放在框架邊界與輸入管理，不能把課堂討論當成已完成的性能證據。

## 本平臺的整合設計

我把 LangChain 定位為工具決策與調度層，把 LlamaIndex 定位為資料層；兩者透過工具合約互通。混合檢索實際合併向量與 BM25，回傳來源讓答案可被檢查。這是使用已有演算法的整合設計，並非聲稱發明 RRF。

MCP 不只作為外接工具：平臺也提供 Server，讓其他客戶端直接取得檢索與 Agent 能力；Client adapter 保留工具 schema。API 另加入 Key 管理、租戶隔離、有限的會話保存與真正串流，將單次腳本轉成持續服務。

快取方面，我選擇可在應用層驗證的事項：固定前綴、固定工具順序、輸入預算、保留最新問題與明確的摘要損失。PagedAttention 的區塊管理屬於後端。沒有 GPU 實驗時，只記錄應用端的字節預算量測，保留待測的 backend 指標。

## 修正後的學習紀錄

測試需要正常載入真正模組：覆寫 sys.modules 的假測試掩蓋了 `platform` 名稱衝突，不能取代本機啟動驗證。僅有 tool 清單也不足以證明 MCP 整合：需要真正完成握手、呼叫檢索與讀取 resource／prompt。

另一個教訓是「摘要」不能直接等同「無損」。保留數值／決策是摘要目標，需要評估；保存原始文字是另一個獨立能力，而且仍有保存期限。串流前的摘要也會增加首 token 前的等待，不能宣稱完全沒有延遲成本。

目前發布準備的範圍是可重現的單程序作品集。後續若要做商用服務，應針對會話持久化、權限、配額、限流、索引更新、摘要質量與推理後端設計新的驗收項目。
